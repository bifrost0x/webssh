# WebSSH 3.2.0

WebSSH 3.2 can be installed from an Unraid template, keeps its application
code read-only for the service user, and keeps custom-UID recovery volumes
provisioned across container recreation. Route settings gain a direct way to
manage jump hosts.

## Highlights

- **Unraid template.** `unraid/webssh.xml` installs the official image with
  the homelab settings of `docker-compose.yml` and runs it as `nobody:users`
  without Linux capabilities and without setuid privilege gains. Unraid
  creates the appdata folders for that user, so the first start needs no
  manual permission step. A test keeps the template's ports, paths and
  variables in sync with `docker-compose.yml`, and the container checks start
  the shipped template. See
  [Install on Unraid](../wiki/Install-on-Unraid.md). (#346)
- **Read-only application code.** Code under `/app` belongs to root and is not
  writable by the service user; only `/app/data` and `/app/recovery` are. A
  compromised process can no longer change code that later starts or health
  checks run. (#346)
- **Custom-UID recovery volumes.** The image ships a placeholder in
  `/app/recovery`, so a recovery volume provisioned for a custom `user:` keeps
  its ownership when the container is recreated before its first start.
  (#345)
- **Clearer start-up errors.** A data directory owned by another user stops
  the container with the required `chown` command. A numeric user without a
  writable home gets a private Gunicorn runtime directory instead of a control
  socket error. (#346)
- **Manage jump hosts from route settings.** The connection dialog and the host
  editor offer a "Manage jump hosts" button next to the SOCKS5 proxy button.
  (#343)

## Upgrade and recovery

No data format changes. Existing Compose files, named volumes and bind mounts
keep working; the image still runs as UID/GID 1000. Rolling back to 3.1.0 with
the same volumes works.

Behaviour changes to check before upgrading:

- `flask --app start:app backup create --confirm-offline` without
  `--destination` no longer writes into `/app`. It uses the private directory
  under `BACKUP_TEMP_DIR` and prints the archive path; with the supplied
  Compose files that is the persistent recovery volume.
- A custom write path under `/app` without its own volume, for example
  `DATA_DIR=/app/custom`, now stops the container at start. Such data was lost
  on every image update before. Mount a volume at that path or keep the
  defaults.
- Derived images that write into `/app` at runtime as the service user must
  write to a mounted volume instead.

See [Upgrading, Rollback, and FAQ](../wiki/Upgrading-Rollback-and-FAQ.md).
